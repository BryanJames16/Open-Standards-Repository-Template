# Glossary

Short definitions of terms used in this repository. A standards project may add terms specific to its subject area.

| Term | Meaning |
| --- | --- |
| **Consensus** | A decision reached after relevant views and objections have been considered. It does not necessarily mean unanimity. The project's governance defines how consensus is determined. |
| **Contributor** | A person who submits proposals, text, feedback, corrections, or other work to the project. |
| **Decision record** | A record of a formal project decision and, where useful, its rationale. |
| **Draft** | A specification or proposal that is still being developed or reviewed and is not yet an approved publication. |
| **Maintainer** | A person responsible for repository administration and helping contributions follow the project's process. Repository access does not automatically grant standards-approval authority. |
| **Normative** | Text that states requirements or rules that a conforming implementation or process is expected to follow. |
| **Informative** | Explanatory material that helps readers understand a specification but does not itself establish requirements. |
| **Proposal** | A request to introduce a new specification or make a change to an existing one. |
| **Public review** | A defined period during which people can review a draft and submit comments. A project uses this when its governance or lifecycle requires it. |
| **Specification** | A document that describes agreed requirements, interfaces, methods, or other technical or procedural details. |
| **Superseded** | Replaced by a newer approved version or publication. The earlier version may remain available for reference. |
| **Deprecated** | Marked as no longer recommended or supported, while possibly remaining available for compatibility or historical reference. |
| **Comment disposition** | The recorded response to a review comment, such as accepted, partially accepted, declined, or deferred, with an explanation where useful. |
| **Publication** | An approved specification or other project work product made available as an official release. |

## Normative Language

If a specification uses uppercase terms such as **MUST**, **SHOULD**, or **MAY**, define their meaning in that specification or reference the terminology convention the project has adopted. Do not assume every reader will interpret these terms in the same way.
